# 調査報告書: ライブトレードにおける取引頻度の低下について

- **報告日**: 2026-10-19
- **対象システム**: `trade`ブランチ `portfolio_trading_bot.py`(ポートフォリオ強化学習 自動売買システム、mediumモード)
- **関連ブランチ**: `trade`(修正対象)、`datafetch_modeltrain`(学習側、変更なし)

## 1. 発生していた事象

テストトレード開始後、約2週間にわたり取引が1件も発生しなかった。その後、より詳細な期間(2026-09-03〜09-26)のログを取得したところ、同期間中にエントリーが発生したのは2026-09-04の2件のみで、それ以降は一度も新規エントリーが発生していなかった。

## 2. 調査の経緯

### 2.1 MT5実行層の確認

`decision_log_medium.csv`(ライブ実測ログ、2026-09-03〜09-26、5,838行)を集計した結果:

| decision | 件数 | 比率 |
|---|---|---|
| below_threshold | 5,818 | 99.66% |
| existing_position | 18 | - |
| order_sent | 2 | - |
| order_rejected | 0 | - |
| circuit_breaker | 0 | - |

- MT5側の注文拒否(`order_rejected`)は**一度も発生していない**。実際に送信された2件の注文も`retcode: 10009`(正常完了)で成功している。
- サーキットブレーカーも一度も作動していない。
- → **MT5との接続・注文実行ロジックには問題がないと判断**。

### 2.2 モデルの方向アクションの分布

`act_direction`(方向アクション)の絶対値は、平均0.0155、p99で0.0673、最大0.4979であり、新規エントリーの閾値(0.2)を超えたのは期間全体でわずか3/5,838件(0.05%)だった。一方、分析モデルの出力(`prob_0/1/2`, `risk_val`)自体は銘柄ごとに健全なばらつきを保ち続けており、特徴量生成パイプラインが停止・固着している様子はなかった。

→ モデルの入力(特徴量)は生きているが、方向アクションの出力が一貫して閾値を下回っている状態であることを確認。この時点では「市況が静かだったため」なのか「ライブ側の観測生成に何らかの差異があるため」なのかを切り分けられなかった。

### 2.3 ヒストリカルリプレイツールの作成

上記を切り分けるため、`portfolio_trading_bot.py`のライブ観測生成パイプラインをそのまま再利用し、過去の任意時点のデータに基づいて同じ推論を再現する検証専用ツール(`historical_datafetch.py`, `historical_replay.py`, `verify_historical_vs_live.py`)を作成した。これらは実際の注文を一切送信せず、信号のみを再現・記録する設計とした。

このツールの開発過程で、ツール自体に起因する3つの不具合を発見・修正した(いずれも`portfolio_trading_bot.py`本体・ライブ運用には影響しない、検証ツール側のみの不具合)。

1. **取得方向の誤り**: `mt5.copy_rates_from()`は指定時刻から「未来方向」にデータを取得する仕様であり、過去再現の意図と逆方向だった。`copy_rates_range()`を使い、必ず過去方向のみを取得するよう修正。
2. **残高比率の計算誤り**: リプレイ側で`initial_balance`を固定値(1000万)に上書きしていたため、観測ベクトルの`balance_ratio`(実残高 ÷ initial_balance)が実態の1/100程度(約0.01)という、学習時に存在しなかった異常値になっていた。固定値での上書きをやめ、ライブと同じ「初回アクセス時の実残高を基準にする」挙動に戻して修正。
3. **タイムゾームのズレ**: `copy_rates_range`はMT5サーバー時刻を基準に動作するが、指定していた時刻はローカル時刻(Pythonの`datetime.now()`相当)だった。実際に3時間のズレが生じていた。最新ティックのサーバー時刻とローカル時刻の差分を測定し、変換してから問い合わせるよう修正。

これら3つの修正後、`verify_historical_vs_live.py`により「現在時刻」を対象に、ライブ用関数(`get_live_features`)とリプレイ用関数(`get_historical_features`)の出力を直接比較したところ、**全89列について完全に一致**(差分0.0)することを確認した。これにより、特徴量生成パイプライン自体のロジックは正しいことが証明された。

### 2.4 過去日付のリプレイと、ライブ実測値との直接比較

上記3つの不具合修正後、2026-09-04(ライブで唯一エントリーが発生した日)を対象にリプレイを実行したが、`act_direction`が閾値を超える比率は約40%となり、ライブ実測(同日でも大半は閾値未満、2件のみ超過)と大きく異なる結果になった。

パイプラインのロジック自体は「現在時刻」比較で正しいと確認済みだったため、ライブ実測ログと今回のリプレイ結果を、同一タイムスタンプ・同一銘柄で直接突き合わせたところ、以下の通り**分析モデルの入力段階(`prob_0/1/2`, `risk_val`)の時点で既に大きな差異**があることが判明した。

| 列 | 平均差分 | 最大差分 |
|---|---|---|
| prob_0 | 0.1512 | 0.7837 |
| prob_1 | 0.1317 | 0.6641 |
| prob_2 | 0.1119 | 0.7146 |
| risk_val | 0.4265 | 6.0616 |
| act_direction | 0.2400 | 1.2216 |

特にEURUSDでは、ライブでは`prob_0`が0.18〜0.21で安定していたのに対し、リプレイでは同じ時間帯で0.57〜0.75まで時間経過とともに連続的にズレが拡大する現象が見られた。

## 3. 結論

- **モデル・トレーディングボット自体に不具合は見つかっていない**。MT5実行層(注文処理・サーキットブレーカー)、および特徴量生成パイプラインのロジックは、いずれも独立した検証(「現在時刻」でのライブ・リプレイ一致確認)により正しいことを確認済み。
- 2026-09-05以降の取引頻度低下自体は、ライブ運用中にリアルタイムで正しく計算された結果であり、ソフトウェアの欠陥によるものではない。
- 一方で、「その期間の市況が本当に静かだったのか」という市況側の根本原因については、**ヒストリカルリプレイによる検証では結論を出せなかった**。これは、MT5のヒストリカルAPIが、数週間前の過去データを後から取得し直した際に、当時リアルタイムで記録されていた値(特に分析モデルが使う価格・出来高ベースの特徴量)を正確に再現しない、という既知の制約によるものである(RAMなどの「メモリ」の限界ではなく、ヒストリカルデータの再現性・正確性の限界)。この制約はリプレイツール側にのみ影響し、ライブ運用そのものには影響しない。

## 4. 今後の方針

- ヒストリカルリプレイによる過去の再現は、MT5の仕様上信頼性に限界があるため、今後はこの手法に依存しない。
- 代わりに、`decision_log_{mode}.csv` / `trade_log_{mode}.csv`による**継続的なライブ監視**に軸を移す。これは実際にその瞬間に観測された本物のデータを記録するため、再現性の問題が原理的に発生しない。
- 本調査と並行して、VPS無人運用に向けた耐障害性の改善(ログのファイル出力・AutoTrading無効化の検知・ハートビートファイル・プロセス全体のクラッシュ耐性)を`portfolio_trading_bot.py`に実装済み(別コミット、`trade`ブランチ `815d66d`)。
- 今後、過去データを使った厳密なバックテスト(損益シミュレーション込み)が必要になった場合は、ヒストリカルAPI経由のリプレイではなく、実際のライブ運用で蓄積された`decision_log`/`trade_log`の実測データ、またはMT5とは別の信頼できるヒストリカルデータソースの利用を検討する。
